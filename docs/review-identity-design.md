# 登録属性と口コミの公開ラベル: 実装前の設計差分

実会社名・氏名は非公開、公開は一般化した属性とinitialsにする方針を確認済み。これはその実装前設計案。架空データだけのUIと、未適用のidentity-aware SQL/隔離テストまで準備。実データを収集せず、schema/permissions/Authへの適用も行わない。従来の自由なニックネームを本番投稿者情報として採用する前提を停止する。

## 分けるデータ

1. **本人だけが入力・閲覧する登録情報**: 実会社名、氏名、実際の役職。認証IDに紐づくprivate領域に保管。公開RPC、URL、localStorage、ログ、analytics、審査一覧には入れない。identity確認担当に開示するなら、通常の口コミ編集権限とは別に必要範囲を承認する。
2. **公開用の自己申告属性**: 業種、会社規模の区分、公開用役職、氏・名の順のinitials。会社規模や業種を実会社名から勝手に分類しない。公開用役職は実際の職名を表示せず、「部門責任者」「マネジメント職」等の広い役割区分から本人が選択する。下記の5区分を採用し、上下の価値や利用者の優劣を示すラベルにしない。
3. **確認状態**: 自己申告/確認済み/失効と確認対象（アカウントのメール、所属、氏名等）を分ける。必須登録やログインだけで所属・本人確認済みと表示しない。user_metadataやclientのadmin/verifiedフラグを根拠にしない。
4. **投稿者ラベルのsnapshot**: 許可された公開属性だけをserverで合成。投稿時のprofile version・公開ラベルへの同意・同意日時を結びつける。本人確認用データや自由入力の会社名をコピーしない。

## initials

日本語氏名から英字を推測しない。本人が確認した「氏のローマ字」「名のローマ字」を別々に使い、氏→名の順で頭文字を表示する。ローマ字入力を保存する必要がなければ端末内の計算にだけ使い、確認済みinitialsだけを保存する。複合姓や別の名前順も表示previewで本人が確認する。名前の表記から読み方をAIで決めない。

例示用fixtureは全て架空とし、`familyRomanization=Y... / givenRomanization=T...` から `Y・T` とする。実際の利用者名や勤務先をfixtureやテストログへ移さない。UIの架空例はKensho / TaroからK・Tを表示する。

## 公開直前の確認

本人に生成後の文字列をそのまま見せ、「この所属区分・役職・initialsが口コミとともに公開される」ことへの明示同意を取る。会社名を隠しても、業種・規模・役職・initials・来店月の組合せから本人が推測され得ることを伝える。投稿後の公開停止/削除経路も同じ画面から分かるようにする。private保存への同意と一般公開への同意をひとまとめにしない。

## 更新・訂正・削除

安全側の初期案:
- 所属/役職の通常更新は過去の口コミを自動で新しい所属に書き換えない。「投稿時の所属区分・役職（自己申告）」のsnapshotとして扱う。
- 公開属性の修正は新しいpreview/同意を必要とする。レビュー本文を訂正するときも新しい版を審査待ちへ戻す。
- 過去の公開ラベルを残したくない場合は本人がレビューを取り下げ/削除できる。氏名訂正などのprivacy問題は公開停止を先にできるようにする。
- account削除でprivate profileと公開ラベルを含む本人口コミを削除。削除後にsnapshotだけが公開に残る設計にしない。運用ログには本文/氏名/会社名を残さない。profileのみの削除では、作り直しによる濫用を防ぐaggregate counter（actor UUID・操作区分・window開始・件数）を固定windowの運用のため保管し、期限切れ分はpurge実行時に削除する。pilot開始前に実行頻度を確定する。Authアカウント/参加資格/Owner表示は別管理で、アカウントを削除した場合はこれらもcascade対象になる。
- 本人/所属の確認状態が失効した場合、過去のsnapshotを理由に「現在確認済み」と表示し続けない。

## pilotへの影響と停止線

`supabase/proposals/20261005234433_review_pilot_v2.sql` は、privateレビューの権限/再送/訂正/削除/通報を検証する未適用のたたき台。最新版の提案はprivate profileと安全なsnapshotを組み込み、submit時にserverで必須項目・版・同意を確認する。自由なdisplay_name引数は削除し、serverのsnapshot labelを使う。会社名/氏名をclient送信payloadからreviewへ転記させない。

残る決定は、確認担当に開示するprivate項目と権限、自己申告のみで開始するか確認を要求するか、過去snapshot更新の扱い、保管/削除方針。live登録フォーム・profile schema・アクセス権・公開は承認前に作動させない。既存下書きのニックネームは、この決定前のローカル記録だけとして扱う。


## 会員プラン・貢献・初期参加を分ける

本パッチでは権利を発行しない。将来の設計を次の3つに分ける:

- **プラン**: 無料/追加機能プラン。通常の店舗比較と真正な口コミを初期の無料基盤とし、課金は会食案件の整理や条件再利用等の追加機能へ。価格・契約・決済は未決定。
- **貢献による期間付き機能開放**: 実体験のある有益な投稿を運営が承認した場合のfeature entitlement。件数競争や星の高低で自動付与せず、期限・対象機能・取消条件を別に定める。投稿審査の甘化や検索順位の優遇には使わない。
- **初期参加の称号/特典**: 参加履歴を表す独立したrecognition。仮称「プライム」は候補で、本人/所属/口コミ内容が検証済みであることは意味しない。永続特典を設定するなら対象の一段階/固定機能集合を明記し、将来の最上位プランまで無制限に付与する約束にはしない。対象者・条件・名称・期間/永続性は別途承認。

データも `public_profile_snapshot`、`plan_entitlements`、`contribution_entitlements`、`founder_recognition` を混ぜない。どの有料/称号/貢献データも口コミの信憑性・点数・検索順位・削除判断へ入力しない。public author labelへ実名/会社名が漏れる計算経路を作らない。料金を払うほど信用される表示を避ける。

## 次の実装の最小単位

1. 公開用属性とinitials生成のpure function/架空fixture、情報非漏えいテスト。実会社名・氏名はlocalStorage、URL、ログ、公開DTOへ含めない。
2. 未接続の登録フォームと公開表示preview（実情報を送信しない）。氏名/会社名のprivate保存と公開属性snapshotの同意を別に表示。採用した広い役割区分を入力肢に使う。
3. profile+snapshotの新SQL案をprivate pilot案に統合し、本人以外の読取り拒否・server生成・同意版照合・profile変更後の古い承認拒否・削除時cascadeを隔離DBで検証。
4. 正確なmigration/対象project/許可するRPC/投稿者と別審査者/対象店舗/保持期間を示してlive適用承認。UI接続/少数pilot開始はその後。課金/称号/永続特典はこの工程に混ぜない。

これ以上のtier機能や本人確認サービスの導入は、無料の店舗比較と口コミを安全に始めるための必須作業ではない。

## 会員画面の具体案（名称はこの案で進める）

- 無料会員: **Member**
- 将来の追加機能プラン: **Plus**
- 初期参加の称号: **Prime**（「創設メンバー」「Gold/Platinum」等の序列表現は使わない）
- 公開する役割区分: **経営・事業統括 / 部門マネジメント / チームマネジメント / 専門職・実務担当 / その他**。役職の正確な名称とは別に本人が選ぶ。自己申告の区分であり、信用や立場の優劣を示さない。

### 画面1: 登録情報

見出し「まずは、登録情報を。」
説明「会社名・氏名・正式な役職は一般公開されません。公開する内容は次の画面で確認できます。」
必須: 実会社名、氏名、正式な役職。Google/メールのアカウント情報から職業を推測して埋めない。実装時は保存先/目的/扱う担当者/削除方法を示し、private保存への同意を確認する。

実情報はlocalStorageやURLに残さず、入力中だけメモリに置く。閉じる/ログアウトで破棄。次の画面に進むこととサーバーへ登録を送信することを分ける。未接続状態で「登録済み」を出さない。

### 画面2: 公開表示

見出し「口コミには、このように表示されます。」
広い業種・規模の自己申告、上記の役割区分、氏/名の順の確認済みinitialsを選択する。規模を会社名からAIで判定しない。固有の部署名や正式職名は公開ラベルへ入れない。

架空fixtureの表示例: 「製薬業界・大規模企業 / 部門マネジメント / Y・T」
補足: 「所属区分・役割は本人の申告です。」
注意: 「会社名や氏名を隠しても、属性の組み合わせから本人が推測される場合があります。」

公開previewへの同意は初期unchecked。いずれかの公開項目を変えたら同意を解除し、serverでpublic profile versionとsnapshotを照合する。実名/会社名/正式職名を含むprivate objectをpublic componentへ渡さない。

### 画面3: 会員機能と参加特典

Memberの基本機能と、Plusの追加機能、Primeの参加特典を別欄にする。Primeは小さなテキスト称号として扱い、星評価の隣に認証マークのように置かない。「所属確認済み」「レビューが信頼できる」などの文言を出さない。

比較・保存・絞り込み等をどこまで無料にするか、Plusの固定対象、Primeへの継続特典は運営判断の確定後に表示する。期限のない特典を約束するCTAや権利付与はまだ実装しない。初期参加候補10人の招待は運営者が相手を選び、連絡する別工程。登録フォームから知人の氏名/メールを収集しない。


## Owner（運営表示）

Ownerはユーザーが指定した運営者向け表示。`pilot_operator_badges`のserver管理レコードだけが根拠で、会員プラン・Prime・貢献・user_metadataから取得できない。Ownerの行を追加してもeditor membershipは増えない。反対にeditorだから自動でOwnerにすることもない。新しい運営者を勝手に登録しない。

投稿時に運営関係があったことをsnapshotの`operatorAtSubmission`へserverが記録する。現在のOwner表示を取り消しても、投稿時の運営関係を隠さない。Owner表示はレビューの信用・点数・順位を上げず、自己承認禁止は通常のeditorと同じ。デモ画面のOwnerは「運営表示の例」であり、閲覧者の権利を表さない。
